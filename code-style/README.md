# Переносимый комплект Code Style

Статус: версия 1.0 утверждена владельцем 11 октября 2026 года. Источник правил — [CODE_STYLE.md](CODE_STYLE.md). Это отдельный артефакт: он не подключён к приложению, его AGENTS.md, зависимостям и CI.

## Состав

- `.prettierrc.json`, `.prettierignore`, `.editorconfig` — форматирование и редактор.
- `eslint.config.mjs` — JS/TS; дополнительный React-профиль применяется только к JSX/TSX.
- `stylelint.config.mjs` — CSS, ограничения и согласованные группы.
- `tsconfig.base.json` — только согласованные строгие флаги, без выбора runtime и сборки.
- `examples/` — небольшие корректные примеры.
- `package.json`, `package-lock.json` — точные проверенные devDependencies для воспроизводимости комплекта; не заменяют package.json приложения.
- `verify.mjs` — проверка конфигураций на положительных и отрицательных примерах во временном каталоге.
- `VERIFICATION.md` — результаты и ограничения проверки.

Biome не используется. SVGO не входит: оптимизация SVG является отдельной задачей.

## Подключение к новому проекту

1. Скопировать документ в документацию и добавить ссылку из инструкций разработчикам/агентам. Если в проекте есть конфликтующие требования, согласовать их до изменения кода.
2. Перенести конфигурации в корень проекта, объединяя с существующими, а не перезаписывая их без проверки.
3. Установить зависимости из devDependencies этого комплекта. Пакетный менеджер выбирает проект. Пример npm: `npm install --save-dev --save-exact <пакет>@<проверенная-версия>`. Для ESLint сохранять совместимую ветку 9 до проверки поддержки всеми плагинами.
4. Подключить `tsconfig.base.json` через `extends` или перенести три compilerOptions в существующий TSConfig. Runtime, target, module, moduleResolution, lib, JSX и include определяются проектом. Сохранить требования framework.
5. Для TypeScript-файлов ESLint project service должен находить TSConfig, который их включает. В конфигурации `tsconfigRootDir` рассчитан на размещение ESLint-конфига в корне. Для monorepo и файлов вне TSConfig настроить область проверки явно.
6. Указать окружение JavaScript: globals браузера, Node.js или тестового runner. База не выбирает среду; `no-undef` выключен. Для JS его необходимо включить после настройки globals. Для TS неизвестные имена проверяет TypeScript.
7. Для собственных обычных CSS по умолчанию запрещены все селекторы тегов. Reset и базовые стили документа получают явный override `selector-max-type: null`. Для оформления внешнего HTML — отдельный ограниченный override с причиной. Не отключать правило сразу для всех CSS.
8. Для default exports, специальных файлов framework и публичных entrypoints учитывать согласованные исключения. Named exports, имена файлов, папки компонентов и node:-imports проверяются review в базовом комплекте.
9. В React-проекте установить React и его типы по требованиям проекта. В примерах компонент синхронный; async server components имеют другой фактический контракт. Для пользовательских компонентов JSX accessibility-настройки могут потребовать сопоставления с нативными элементами.
10. Проверить инструменты и типы на небольшом участке до массовой миграции; затем просмотреть diff и запустить проектные тесты.

Пример команд проекта после подключения:

```json
{
  "format": "prettier --write .",
  "format:check": "prettier --check .",
  "lint": "eslint .",
  "lint:css": "stylelint \"**/*.css\"",
  "typecheck": "tsc --noEmit"
}
```

Тестовые команды добавляются по фактическому runner. CI запускает проверки без `--fix` и `--write`. Предупреждения не превращаются автоматически в ошибки: `--max-warnings=0` противоречит принятому разделению предпочтений и требований.

Автоисправление запускается локально по проверенной области. После ESLint/Stylelint fix запускать Prettier и повторять проверки. Не применять массовое исправление сортировки кода без просмотра порядка вычислений и побочных эффектов.

## Разделение ответственности

Prettier не запускается как правило ESLint. Форматирующие правила ESLint/Stylelint не включены; `eslint-config-prettier` не нужен для этой базы, но при подключении framework-пресетов нужно заново проверить пересечения.

ESLint содержит выбранные проверки, а не все правила сторонних пресетов. React hooks ограничены правилами вызова и зависимостей; весь compiler-профиль автоматически не принимается. `jsx-a11y` использует recommended-профиль как технический набор частичных проверок доступности.

Stylelint задаёт собственные группы через stylelint-order, без чужого пресета порядка. Список свойств и shorthand конечный: для нового свойства проверить его семантику и дополнить конфигурацию. Нельзя считать неизвестное сокращение разрешённым только потому, что linter его не обнаружил.

Проверки магических чисел и сортировки объектов — предупреждения: алгоритм не понимает бизнес-смысл и порядок выполнения. Соответствующие обязательные требования проверяются дополнительно на review. Предпочтение `type` перед `interface` также предупреждение.

## Для ИИ и review

Краткая инструкция для нового проекта:

> Соблюдай CODE_STYLE.md и конфигурации проекта. Приводи весь изменяемый собственный файл к стандарту; не меняй generated/vendor код. Проверяй значимый порядок до сортировки. Обосновывай исключения локально. Не храни контекст и инструкции для ИИ в комментариях. Не считай отсутствие предупреждения linter доказательством соблюдения смысловых правил.

Нет собственного ESLint-плагина для папок, сокращений, props и сигнатур: эти правила обозначены как review, а не скрыты за обещанием полной автоматизации.

## Проверка самого комплекта

После установки зависимостей в этот каталог:

```sh
npm ci --ignore-scripts
npm run verify
```

Проверка создаёт и удаляет собственный временный каталог. Файлы приложения не читает и не изменяет. Lockfile предназначен для проверки комплекта; при переносе зависимостей используется lockfile целевого проекта.
