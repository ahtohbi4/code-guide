# Личный Code Style для веб-приложений на JavaScript и TypeScript

Версия: 1.0. Документ и комплект конфигураций утверждены владельцем 11 октября 2026 года.

Стандарт предназначен для frontend и backend веб-приложений на JavaScript/TypeScript. React — дополнительный раздел. Для библиотек предусмотрены правила публичного API. Стандарт не назначает framework, инфраструктуру, структуру приложения, bundler или библиотеку валидации.

## 1. Как читать и применять стандарт

**Обязательно** — требование, нарушение которого требует локального обоснованного исключения. **Предпочтительно** — основной вариант, от которого можно отступить по конкретной причине. **Допустимо** — разрешённый вариант в обозначенных условиях. Неавтоматизированное правило сохраняет силу.

Форматирование определяет Prettier; проверяемые ограничения — ESLint, Stylelint и TypeScript. Документ объясняет смысл и ограничения правил. Конфигурации должны соответствовать документу. При обнаружении противоречия его нужно устранить, а не молча выбрать удобный вариант.

При изменении файла весь собственный код этого файла приводится к стандарту. Изменения поведения и механические изменения желательно разделять для review. Сгенерированные файлы и сторонний код не приводятся к личному стилю. Обязательные имена файлов и сигнатуры framework или внешнего API сохраняются.

Локальные исключения сопровождаются коротким объяснением причины. Подавление применяется к минимальной области. Не отключать проверку проекта или файла, если достаточно отдельной строки. Обоснование должно быть полезно следующему разработчику.

```ts
// Внешний SDK использует такую сигнатуру; изменить её на стороне клиента нельзя.
// eslint-disable-next-line max-params
const sdkCallback = (event: Event, source: string, timestamp: number): void => {
  handleSdkEvent({ event, source, timestamp });
};
```

## 2. Общие принципы

- **Предпочтительно:** читаемость важнее минимального количества символов. Именованные промежуточные значения допустимы, если объясняют смысл.
- **Предпочтительно:** небольшое дублирование лучше преждевременной абстракции. Общее выделяется по подтверждённому повторению смысла и понятному контракту.
- **Обязательно:** не добавлять опции, props, обёртки и гибкость только на будущее.
- **Предпочтительно:** функции и обычные объекты; классы — при необходимости экземпляров с поведением и состоянием либо по требованиям API/framework.
- **Обязательно:** не жертвовать валидацией, обработкой ошибок, сохранностью данных и accessibility ради краткости.

## 3. Именование, файлы и модули

### 3.1. Имена

| Сущность                                 | Правило            | Пример                        |
| ---------------------------------------- | ------------------ | ----------------------------- |
| Переменные, функции, параметры           | `camelCase`        | `orderTotal`, `parseResponse` |
| Типы, интерфейсы, классы, компоненты     | `PascalCase`       | `PaymentResponse`, `Button`   |
| Фиксированные константы в начале модуля  | `UPPER_SNAKE_CASE` | `MAX_RETRIES`                 |
| Обычные файлы и каталоги                 | `kebab-case`       | `payment-client.ts`           |
| Каталог и основной файл React-компонента | `PascalCase`       | `Button/Button.tsx`           |

**Обязательно:** полноценные понятные имена. Однобуквенные имена разрешены только для индексов циклов. Иные сокращённые имена требуют явного согласия разработчика. Устоявшиеся термины `id`, `url`, `api`, `http` допустимы; сокращения `usr`, `btn`, `val` не использовать. Не добавлять префиксы `I` и `T` к обычным именам интерфейсов и типов.

Булевы значения читаются как утверждения: `isLoading`, `hasAccess`, `canSubmit`, `shouldRetry`. Избегать отрицаний вроде `isNotReady`. Стандартные атрибуты и свойства `disabled`, `hidden` допустимы.

`const` не делает объект неизменяемым. Функции, компоненты и вычисляемые значения уровня модуля не переводятся в `UPPER_SNAKE_CASE` только из-за своего расположения.

### 3.2. Константы и магические числа

**Обязательно:** числа с неочевидным смыслом выносить в именованные константы: таймауты, лимиты, коэффициенты, бизнес-пороги. В имени по необходимости указывать единицу, например `REQUEST_TIMEOUT_MS`.

Очевидные `0`, `1`, индексы и простая арифметика допустимы, когда смысл понятен. Не создавать константу `ZERO` ради запрета числовых литералов. Именование не заменяет обоснование выбранного значения.

```ts
// Плохо: неизвестно, что означает число.
setTimeout(retryRequest, 3000);

// Хорошо.
const RETRY_DELAY_MS = 3000;
setTimeout(retryRequest, RETRY_DELAY_MS);

if (items.length === 0) {
  return;
}
```

### 3.3. Сортировка

**Обязательно:** алфавитная сортировка там, где порядок не влияет на поведение или контракт: imports, именованные exports, свойства объектов и типов, JSON, JSX props. В определениях типов обязательные поля идут перед необязательными; каждая группа сортируется отдельно. В деструктуризации и JSX — общий алфавитный порядок.

Порядок сравнения по умолчанию — алфавитный без учёта регистра (настройка проверок, а не отдельное бизнес-правило). `type` не участвует в сравнении имени импортируемого символа.

**Обязательно:** сохранять значимый порядок. Это относится к вычислениям значений, getters, spread, повторным ключам, порядку обхода объекта, значениям параметров по умолчанию и регистрации побочных эффектов. Порядок arrays не менять, если они задают последовательность. Исполняемые инструкции и объявления функций располагаются по логике чтения, а не по алфавиту.

### 3.4. Imports и exports

- **Обязательно:** imports находятся в начале модуля; директивы среды вроде `'use client'` могут предшествовать им.
- **Обязательно:** исключительно типовые импорты — `import type`. При импорте значений и типов из одного модуля использовать один import с inline `type`, когда синтаксис и контракт позволяют.
- **Обязательно:** не переставлять imports с побочными эффектами без проверки порядка выполнения.
- **Предпочтительно:** named exports. Default export — по требованию framework или внешнего контракта.
- **Обязательно:** экспортировать только необходимые сущности.
- **Допустимо:** `index.ts` как публичный API модуля или библиотеки; не создавать в каждой папке.
- **Предпочтительно:** ESM. CommonJS — по требованиям среды или существующего контракта.
- **Обязательно:** встроенные модули Node.js импортировать с `node:`.
- **Обязательно:** сетевые запросы, таймеры и изменения внешних данных не запускаются просто при импорте обычного модуля. Инициализация явная; специальные entrypoints и регистрационные модули могут иметь документированные побочные эффекты.

```ts
import { createClient, type ClientOptions } from './client';
import type { PaymentResponse } from './payment-response';
```

## 4. Форматирование

| Настройка                            | Значение                                              |
| ------------------------------------ | ----------------------------------------------------- |
| Отступ                               | 2 пробела, без табов                                  |
| Длина строки                         | 100 символов — ориентир formatter, не жёсткий предел  |
| Кавычки JS/TS                        | Одинарные по умолчанию                                |
| Кавычки HTML/JSX                     | Двойные                                               |
| Точки с запятой                      | Обязательны                                           |
| Завершающие запятые                  | В многострочных конструкциях, где допускает синтаксис |
| Скобки параметров стрелочных функций | Всегда                                                |

Prettier может выбрать другой вид кавычек, чтобы избежать лишнего экранирования. JSON следует собственному синтаксису: двойные кавычки, без завершающих запятых. Template literals используются для интерполяции или многострочного текста.

Переносы операторов и выражений определяет formatter. Пустые строки разделяют смысловые этапы; не отделять каждое объявление пустой строкой и не использовать несколько пустых строк подряд.

**Обязательно:** фигурные скобки у управляющих блоков, даже для одного действия. У `if` условие в круглых скобках, `) {` на одной строке, тело с новой строки, закрывающая `}` с новой строки.

```ts
if (value === '') {
  return;
}
```

Неявный возврат стрелочной функции допустим для простого выражения. Несколько действий — блок с явным `return`, если функция возвращает значение.

## 5. JavaScript

### 5.1. Переменные и функции

- **Обязательно:** `const`, если нет переназначения; `let` только с явным последующим переназначением. `var` запрещён.
- **Предпочтительно:** стрелочные функции. `function` — только когда нужны его особенности, например собственный `this` или генератор.
- **Обязательно:** собственная функция с количеством параметров больше двух принимает объект параметров. Сигнатуры сторонних callbacks и переопределяемых методов сохраняются по контракту.
- **Обязательно:** избегать неясных булевых позиционных настроек вроде `saveOrder(order, true, false)`.
- **Допустимо:** у обычных функций деструктурировать объект прямо в параметрах. Для React действует отдельное правило.

### 5.2. Условия и значения

- **Обязательно:** `===` и `!==`, включая проверки `null`/`undefined` вместо `value == null`.
- **Предпочтительно:** ранние возвраты вместо глубокой вложенности.
- **Допустимо:** тернарный оператор для простого выбора значения; вложенные тернарные запрещены.
- **Обязательно:** `??` для подстановки только при `null`/`undefined`; `||` — когда нужно заменить также `0`, `false`, `''`.
- **Обязательно:** булевы значения проверять непосредственно; смысл проверок строк и чисел выражать явно.
- **Обязательно:** optional chaining обслуживает ожидаемо необязательные данные, а не скрывает нарушение обязательного контракта.

```ts
const limit = requestedLimit ?? DEFAULT_LIMIT;

if (canSubmit && items.length > 0) {
  submitOrder();
}
```

### 5.3. Коллекции

`map` — преобразование; `filter` — отбор; `find` — поиск. Для действий, раннего выхода и последовательного `await` предпочитать `for...of`. `forEach` не запрещён для синхронных действий. `reduce` допустим, если накопление читается проще обычного цикла. Не использовать `map` ради побочных эффектов.

Не изменять входные объекты и массивы без явного контракта. Например, `sort()` входного массива меняет исходные данные; использовать копию или подходящую неизменяющую операцию. Локальное изменение собственных данных допустимо.

## 6. TypeScript

- **Обязательно:** `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` в новых проектах.
- **Обязательно:** непроверенные внешние данные — `unknown`; runtime-проверка до использования.
- **Обязательно:** явный `any` запрещён по умолчанию. Локальное исключение допускается при конкретном ограничении стороннего API, с объяснением.
- **Предпочтительно:** `type`; `interface` при необходимости declaration merging или контракта библиотеки.
- **Обязательно:** параметры типизируются явно, если тип не задаёт контекст.
- **Обязательно:** экспортируемые функции и публичные методы имеют явный возвращаемый тип.
- **Предпочтительно:** вывод типов для внутренних функций и переменных, без `const count: number = 0`.
- **Обязательно:** `as` только при конкретном основании, которое TypeScript не может вывести; assertion не заменяет runtime-проверку.
- **Обязательно:** двойное приведение `as unknown as SomeType` и `value!` запрещены по умолчанию; исключение требует объяснения.
- **Предпочтительно:** `satisfies` для проверки соответствия объекта типу с сохранением выведенного типа.
- **Предпочтительно:** `readonly` для входных коллекций и полей, которые нельзя изменять. Это проверка типов, а не глубокая runtime-заморозка.
- **Предпочтительно:** unions строковых литералов; если нужны runtime-значения — объект или массив с `as const`. `enum` по требованию существующего контракта.

```ts
type RequestOptions = {
  endpoint: string;
  timeoutMs: number;
  headers?: Readonly<Record<string, string>>;
};

export const countItems = (items: readonly string[]): number => items.length;

type PaymentState = 'created' | 'failed' | 'pending';
```

## 7. Ошибки и асинхронный код

### 7.1. Promises

**Предпочтительно:** `async/await`; `.then()` допустим, если понятнее. Каждый promise возвращается вызывающему коду, ожидается или имеет явную обработку ошибки. `void operation()` сам по себе не считается обработкой ошибки.

**Обязательно:** не использовать `async` callbacks в `forEach`. Метод не ожидает и не собирает promises, внешний `try/catch` не перехватывает их отклонения. `await items.forEach(...)` проблему не решает.

```ts
// Последовательные операции.
for (const order of orders) {
  await saveOrder(order);
}

// Независимые операции при допустимой нагрузке.
await Promise.all(orders.map((order) => saveOrder(order)));
```

Параллельность допускается, когда порядок и ограничения ресурсов позволяют. `Promise.all` не отменяет уже запущенные операции при отклонении одного promise. У незавершённых фоновых операций должен быть понятный жизненный цикл.

### 7.2. Ошибки

- Ловить ошибку там, где можно восстановиться, добавить контекст или перевести её в ответ вызывающей стороне.
- Не добавлять `try/catch`, который только повторно бросает ту же ошибку.
- Не оставлять пустой `catch`; намеренное игнорирование требует причины.
- Не превращать ошибку в успешное пустое значение без явного контракта.
- Бросать `Error` или его наследника. При оборачивании сохранять исходную причину, если среда поддерживает `cause`.
- Ожидаемые исходы должны явно различаться вызывающим кодом. Форма по контракту: union результата, `null` для отсутствия или исключение. Универсальный `Result` для всего приложения не обязателен.

## 8. HTML и JSX

### 8.1. Семантика

- **Обязательно:** действие — кнопка, переход — ссылка; выбирать подходящий нативный элемент.
- **Обязательно:** не выбирать тег ради краткости или стилизации вопреки семантике. `<i>` не служит универсальным контейнером иконок или бейджей.
- `div`/`span` допустимы для группировки без собственного семантического смысла.
- Нативный элемент предпочтительнее самостоятельного воспроизведения его поведения через ARIA.
- Заголовки отражают иерархию содержания, уровень не выбирается ради размера текста.
- Для обычной страницы по умолчанию один основной `main` и один `h1`, описывающий содержание. Исключения обоснованы.
- `section` — тематический раздел, обычно с заголовком. Не добавлять семантические контейнеры только для стилей.
- Убирать лишние контейнеры. Выделять разметку по понятной ответственности или для читаемости; фиксированного лимита строк и вложенности нет.

### 8.2. Формы

Каждому полю — доступное имя; видимый `label` по умолчанию. Placeholder не заменяет label. Связанные поля группировать через `fieldset`/`legend`, когда соответствует смыслу. У кнопок явно задавать `type`. Ошибки описывать текстом и программно связывать с полями. Использовать подходящие `type` и `autocomplete`.

### 8.3. Атрибуты

В JSX сортировать атрибуты по алфавиту, сохраняя значимый порядок относительно spread. Булево `true` — кратко: `<Button disabled />`. Строки — `label="Save"`, выражения — `label={buttonLabel}`. JSX без children — самозакрывающийся элемент. Обычный HTML сохраняет собственный синтаксис: `<input>`, без обязательного `/>`.

```tsx
<button disabled={isSubmitting} onClick={handleSubmit} type="submit">
  Save
</button>
```

## 9. Accessibility

- Смысловым изображениям — содержательный `alt`; декоративным — `alt=""`.
- Декоративные иконки скрывать от accessibility tree.
- Кнопке с одной иконкой — доступное имя действия.
- `title` не обязателен для каждого SVG; решение зависит от назначения.
- Интерактивные элементы доступны с клавиатуры; фокус видим.
- Не убирать outline без равноценной замены.
- Не использовать положительный `tabIndex`.
- DOM-порядок обеспечивает понятную последовательность чтения и фокуса.
- Собственные сложные виджеты имеют соответствующее управление клавиатурой и фокусом.
- Информация не доступна исключительно через hover.
- Содержание и функциональность сохраняются при увеличении текста до 200% и пользовательском изменении текстовых интервалов. Это поведенческая проверка, а не запрет конкретных единиц CSS.

Автоматические проверки не подтверждают доступность интерфейса целиком; необходима проверка поведения.

## 10. CSS

### 10.1. Селекторы и имена

- Классы — основной способ стилизации компонентов; ID не используются для стилей.
- Селекторы тегов допустимы в reset и базовых стилях документа.
- Единая базовая специфичность компонентов; повышение только для состояний или другой явной необходимости.
- Не зависеть от глубокой DOM-структуры. Псевдоклассы, псевдоэлементы и селекторы состояния допустимы.
- Стилизация по вложенному тегу (`.card span`) запрещена в компонентах. У дочернего элемента собственный класс.
- Локальное обоснованное исключение: изолированное оформление внешнего HTML, например статьи из Markdown, где невозможно назначить классы каждому элементу.
- Обычный CSS — `kebab-case`; BEM для компонентов в общем пространстве имён, когда нужна явная связь элементов и модификаторов. BEM не обязателен везде.
- CSS Modules допускают `camelCase` для обращения через `styles.someClass`.

### 10.2. Свойства и порядок

**Обязательно:** shorthand запрещены, кроме `border`, `margin`, `padding`. Это касается и `background`, `font`, `flex`, `grid`, `gap`, `inset`, `overflow`, `outline`, `animation`, `transition`. Вместо `gap` использовать `column-gap` и `row-gap`; вместо `border-radius` — отдельные свойства углов. Разрешённый `border` намеренно сбрасывает затрагиваемые значения.

Порядок групп; внутри каждой алфавитный порядок. Между непустыми группами пустая строка.

| Группа | Содержание                                                                          |
| ------ | ----------------------------------------------------------------------------------- |
| 1      | Локальные custom properties                                                         |
| 2      | Позиционирование и слои: `position`, `inset-*`, `top`, `z-index`                    |
| 3      | Layout: `display`, `align-*`, `flex-*`, `grid-*`, `column-gap`, `row-gap`, `order`  |
| 4      | Размеры и блочная модель: `box-sizing`, размеры, `margin`, `padding`                |
| 5      | Типографика: `color`, `font-*`, `line-height`, `text-*`, `white-space`              |
| 6      | Внешний вид: `background-*`, `border*`, `box-shadow`, `opacity`, `outline-*`        |
| 7      | Переполнение и взаимодействие: `cursor`, `overflow-*`, `pointer-events`, `scroll-*` |
| 8      | Преобразования и анимация: `animation-*`, `transform`, `transition-*`               |

Точное распределение распространённых свойств задано в `stylelint.config.mjs`. Неописанное свойство временно располагается после групп по алфавиту; при использовании его классификацию уточняют. Это ограничение списка конфигурации, а не разрешение обходить смысл групп.

Fallback, повторные свойства и значимые сочетания shorthand/longhand сохраняют порядок. Такие участки исключаются из автоматической сортировки локально с причиной.

### 10.3. Значения и размеры

- Повторяющиеся значения с общим смыслом — CSS custom properties.
- Цвета темы, основные интервалы и размеры типографики — согласованные tokens.
- Не превращать каждое одноразовое значение в переменную.
- Ноль без единицы там, где синтаксис допускает.
- **Предпочтительно:** `px` для типографики, интервалов и фиксированных размеров, включая `line-height`.
- Размер текста и высота строки согласованы; при изменении `font-size` проверять `line-height`.
- `%`, `fr`, viewport units и другие относительные единицы допустимы для относительной геометрии и адаптивности.
- `rem`, `em` и безразмерный `line-height` допустимы по конкретной необходимости, но не являются предпочтением.
- Целые `px` в CSS не гарантируют отсутствие дробных координат после масштабирования и отображения на устройстве.
- Высоту не задавать без явной необходимости: высотой управляет контент. `min-height` допустим для обоснованной стартовой высоты. `height` допустим, например, для иконок, карты или виртуализированного списка.

### 10.4. Адаптивность и состояния

Mobile-first предпочтителен для адаптивных экранов, исключения по задаче. Не скрывать overflow для маскировки ошибки layout. Logical properties применять, когда направление письма имеет значение; физические свойства — для физических направлений.

`!important` запрещён по умолчанию; локальное исключение с причиной возможно, например для сторонних стилей. Вложенность должна сохранять понятность селектора; численного лимита нет.

Стилизовать используемые hover, focus-visible, active и disabled состояния. Учитывать `prefers-reduced-motion` для несущественной анимации. Анимируемые свойства перечислять явно; `transition-property: all` не использовать.

## 11. React — дополнительный раздел

### 11.1. Компоненты и файлы

**Обязательно:** строго один компонент на файл, включая внутренние и тестовые компоненты. JSX непосредственно внутри теста допустим. Каждый компонент в обязательной папке своего имени, даже если содержит один файл.

```text
components/
  Button/
    Button.module.css
    Button.test.tsx
    Button.tsx
```

Необязательные файлы не создавать заранее; `index.ts` не добавлять автоматически. Внутренний компонент имеет собственную папку рядом или внутри родителя по области использования. Стандарт не требует папку `components` именно в корне проекта.

Компоненты — стрелочные функции, отдельный тип `ComponentNameProps`. `React.FC` не использовать по умолчанию. `children` объявлять явно, если поддерживается. Тип props экспортировать только при необходимости для потребителей, в том числе публичного API библиотеки.

**Обязательно:** принимать объект `props`, деструктурировать внутри тела. Обычный синхронный компонент возвращает явно указанный `ReactElement`, допускающий отсутствие разметки — `ReactElement | null`. Иные формы по фактическому контракту, например асинхронный серверный компонент.

```tsx
import type { ReactElement } from 'react';

type ButtonProps = {
  label: string;
  disabled?: boolean;
};

export const Button = (props: ButtonProps): ReactElement => {
  const { disabled, label } = props;

  return (
    <button disabled={disabled} type="button">
      {label}
    </button>
  );
};
```

### 11.2. Props и состояние

Не изменять props/state напрямую. Не хранить в state значение, вычисляемое из текущих props/state. Для обновления, зависящего от предыдущего значения, использовать функциональную форму. Не добавлять универсальные props на будущее.

Spread props допустим для намеренной передачи атрибутов и композиции; контракт явный. Не передавать внутренние props в DOM без разбора.

### 11.3. Hooks и эффекты

- Собственные hooks — `useSomething`.
- Hooks вызываются в допустимых React местах; специальные API с отдельными правилами рассматриваются по своему контракту.
- Зависимости hooks полные; подавление проверки требует причины.
- Effects — синхронизация с внешними системами; пользовательское действие — обработчик события.
- Подписки, таймеры и другие ресурсы освобождаются при необходимости.
- Собственный hook выделять для связной логики, а не просто ради уменьшения компонента.
- `memo`, `useMemo`, `useCallback` — при измеренной проблеме производительности или конкретной необходимости стабильной ссылки.

### 11.4. События и списки

Props событий — `onSubmit`, `onSelect`; внутренние обработчики — `handleSubmit`, `handleSelect`. Простой inline callback допустим, сложный выносится в именованную функцию. Создание новой функции при рендере само по себе не повод запретить inline callbacks.

`key` — стабильный идентификатор. Индекс допустим только для статичного списка с неизменным составом и порядком. Случайные keys запрещены. Для числового условия — явная проверка (`items.length > 0 && ...`). Сложные условия — именованные значения или отдельные ветки, без вложенных тернарных.

## 12. Backend и публичный API библиотек

Входные данные проверяются во время выполнения; тип TypeScript не заменяет валидацию. Запросы и непроверенные ответы внешних сервисов недоверенные. Конфигурация проверяется до использования с понятной ошибкой. После установленной границы доверия не дублировать ту же проверку в каждом внутреннем вызове. Конкретная библиотека не назначается.

Не логировать секреты, токены и чувствительные данные. Не отдавать клиенту stack trace и внутренние детали. Диагностический лог даёт контекст операции; избегать повторного логирования одной ошибки на каждом слое. Временные отладочные логи удалять. Инструмент логирования выбирает проект.

Публичный API библиотеки:

- Экспортировать только поддерживаемый контракт, не внутренние детали.
- В публичном entrypoint явно перечислять exports вместо `export *`.
- Не импортировать внутренние файлы библиотеки в обход публичного API.
- Документировать ошибки, существенные побочные эффекты и ограничения публичных функций.
- Bundler, форматы сборки и структура пакетов не фиксируются стандартом.

## 13. Комментарии и документация

Идентификаторы на английском; комментарии, названия тестов и документация на языке команды. Этот стандарт на русском.

Комментарий объясняет причины, ограничения и неочевидные решения, не пересказывает код. Публичный API библиотеки документируется по назначению, ограничениям, ошибкам и существенным побочным эффектам. JSDoc применяется для документации потребителю API; обычный комментарий — для внутренней причины.

`TODO` описывает конкретную оставшуюся работу; ссылка на задачу добавляется, если она существует. Закомментированный код удаляется, история остаётся в Git.

**Обязательно:** не использовать комментарии в коде как дополнительное хранилище знаний для ИИ: контекста диалога, инструкций агентам, истории решений и заметок для следующего запуска. Значимые знания размещаются в документации проекта. Комментарий рядом с кодом сохраняется только при пользе для понимания этого кода человеком.

## 14. Тесты

- Проверять наблюдаемое поведение и существенные риски: бизнес-правила, валидацию, ошибки, регрессии. Не повторять реализацию тестом и не проверять тривиальные детали.
- Подготовка → действие → проверка; один связный сценарий на тест. Несколько assertions допустимы. Комментарии Arrange/Act/Assert не обязательны.
- Название описывает условие и ожидаемый результат на языке команды.
- Unit-тест рядом: `module-name.test.ts`; компонент — `ComponentName.test.tsx` в его папке.
- Интеграционные и end-to-end тесты — отдельно по conventions проекта.
- Подменять внешние границы, не каждую внутреннюю функцию. Реальные простые объекты предпочтительнее mocks, когда достаточны.
- Данные показывают условия сценария; общие fixtures по подтверждённому повторению.
- Состояние mocks и окружения не утекает между тестами; порядок запуска не влияет на результат.
- Ожидать асинхронные операции; произвольные задержки запрещены. Ждать конкретное состояние/событие; временем управлять тестовыми средствами при проверке таймеров.
- Snapshots только для компактного, понятного, полезного результата; изменения проверяются содержательно.
- Общий процент coverage и тестовый framework стандарт не назначает.

## 15. Проверки и ограничения автоматизации

CI проверяет форматирование, lint, типы и согласованные тесты без изменения файлов. Обязательные нарушения блокируют проверку. Предпочтения — предупреждения либо review. Автоисправление локально допустимо; изменения, способные повлиять на поведение, проверяются по diff.

| ------------------------------------------------------------ | ---------------------------------------- | ----------------------------------------------------------------------- |

| Возвращаемые типы публичных функций                          | typescript-eslint + review               | Публичные методы дополнительно проверяются review                       |
